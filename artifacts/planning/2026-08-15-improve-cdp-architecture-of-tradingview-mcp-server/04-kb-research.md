## Knowledge Base Findings

The concept-rag library was queried on three research axes. Coverage is thin for this package's domain — the library holds database-systems and pattern-catalog texts, not browser-automation or Electron-CDP material. Two findings nonetheless carry weight; the gap itself is recorded as a finding.

1. **Connection pooling: account for non-immediate close.** From *Database System Concepts ISE*: when connection pooling is in use, a connection may not be returned to the pool (or closed) immediately, and diagnostics must account for that. Application here: R1's transport-provided scoped-client factory must treat client teardown as asynchronous — a scoped client that has been released by its caller is not necessarily closed at the socket level yet, so pooling/reuse logic must key on lifecycle state, not on the caller's handle. Directly informs the design of the factory's release semantics.
2. **Pattern-catalog orientation.** *Pattern-Oriented Software Architecture Vol. 4* and a pattern-description schema surfaced for the layered/registry axes — confirming that "layered architecture" and "registry / single source of truth" are established named patterns rather than ad-hoc constructions, so R2 (path registry) and the transport-layer consolidation (R1/R3) can be framed and reviewed as standard pattern applications. No specific implementation guidance beyond that.
3. **Gap noted.** The knowledge base holds no relevant content on Chrome DevTools Protocol, Electron CDP endpoints, WebSocket session management, or MCP server architecture. The package's research weight therefore rests on web sources and the in-repo prior research. This gap is expected (the library is domain literature, not tooling docs) and is recorded per the research protocol rather than silently bypassed.

## Web Research Findings

All web findings were validated on recency, authority, relevance, and consistency per the source-validation rule. Each carries its URL and its application to this package.

1. **chrome-remote-interface: concurrent sessions are supported; one CDP instance per session, browser target for management.** (cyrus-and/chrome-remote-interface [issue #533](https://github.com/cyrus-and/chrome-remote-interface/issues/533), maintainer answer; and [issue #531](https://github.com/cyrus-and/chrome-remote-interface/issues/531) on browser-target sessions.) Application to R1: the upstream library the server already depends on explicitly supports multiple concurrent sessions, and its maintainer recommends a *browser-level* session for managing per-target sessions. This validates R1's scoped-client factory — per-target clients are a supported, sanctioned usage — and identifies the browser target as the natural management/control channel for the connection module's target listing (R1's `listTargets()` consolidation), rather than re-fetching `/json/list` at five sites.
2. **Flattened `Target.attachToTarget` with per-command `sessionId` is the canonical multi-tab control path.** (Stack Overflow, [Chrome DevTools Protocol: control new tabs](https://stackoverflow.com/questions/45637320/chrome-devtools-protocol-control-new-tabs), accepted/working answer; corroborated by mafredri/cdp [issue #33](https://github.com/mafredri/cdp/issues/33).) Application to R1/R3: there are two architecturally distinct multi-target designs — N sockets (one per target, current bypass-site approach) versus one socket + flattened sessions. R1's pool stays with N sockets (minimal change, matches the existing per-target `webSocketDebuggerUrl` flow), but the flatten-session alternative is now documented as the community-canonical option; it becomes a *recorded rejected path* for this package (larger rewrite, no behavioral requirement demands it) and a genuine candidate for the out-of-scope event-driven follow-up.
3. **Browser-side WebSocket limits are real but high (~30 per host, ~255 global in Chromium); the contention fix is about endpoint behavior, not numeric exhaustion.** (websocket.org, [WebSocket Connection Limits](https://websocket.org/guides/connection-limits/); Chromium socket-pool constants via [Stack Overflow](https://stackoverflow.com/questions/26003756/is-there-a-limit-practical-or-otherwise-to-the-number-of-web-sockets-a-page-op); flutter/devtools [issue #8298](https://github.com/flutter/devtools/issues/8298) and Dart-Code [issue #5229](https://github.com/Dart-Code/Dart-Code/issues/5229) as real-world contention incidents.) Application to R1/SC-7: the observed `TV_CDP_BUSY` wedges at a handful of sockets are far below any numeric limit, so the wedge is consistent with the *server-side* devtools endpoint closing fresh sockets while busy (as `withTargetEvaluate`'s header records), not client-side numeric exhaustion. Consequence: R1's bounded pool with retry/backoff is the right-sized fix; there is no evidence demanding the heavier flatten-session redesign, and SC-7's smoke-level scenario (no `TV_CDP_BUSY` under parallel-tab work) is a proportionate verification bar — this supports the agent's position on assumption RE-4.
4. **Condition polling with a dedicated sleep primitive is the established replacement for ad-hoc `setTimeout` sleeps.** (ccollier86/waitfor [README](https://github.com/ccollier86/waitfor); axtk/promisify-polling [README](https://github.com/t8js/promisify-polling); pinterval [npm](https://registry.npmjs.org/pinterval); Node `timers/promises` guidance via [Wait & Sleep in NodeJS](https://useaxentix.com/blog/javascript/wait-sleep-in-nodejs-complete-guide/).) Application to R4: community practice converges on (a) one shared promise-based sleep, (b) bounded poll-until-condition with timeout where a condition can be named, (c) retained fixed delays where it genuinely cannot. The package already holds both primitives (`wait.js` structured waits, `dom.js` bare sleep) with in-tree adopters — external practice therefore validates the comprehension finding that R4 is an *adoption sweep* with a per-site policy decision, not new infrastructure, and no third-party wait library is warranted.
5. **Corroboration already in repo.** The prior research report ([02-external-research-and-opportunities.md](../2026-08-15-tradingview-mcp-cdp-architecture/02-external-research-and-opportunities.md)) surveyed community implementations (mcp-chrome, chrome-cdp-skill, cw-hkitteh), the TradingView JS-manager catalog (socket/quote/session/chart managers), connection-pooling and event-driven designs, and unadopted CDP capabilities (Target, Inspector, Network, Page, Runtime, ServiceWorker, Accessibility), with the research→architecture mapping and build order in §6. This activity treats that report as the primary external base and adds the four findings above; nothing found this pass contradicts its mapping or its build order.

## Applicable Patterns

1. **Connection pool with lifecycle-aware release (R1)** — scoped-client factory keyed by target, async teardown treated as non-immediate (KB 1). Bounded: default reuse of the shared client for the active tab, private sockets only for background-tab/shell-window access, all from one factory.
2. **Registry / single source of truth (R2)** — every page-path read routed through `KNOWN_PATHS` getters; literal bindings removed in a mechanical sweep.
3. **Layered architecture / facade (R1, R3)** — CDP protocol domains owned by the transport/protocol layer; consumers hold no raw client objects; `/json/list` exposed once as `listTargets()`.
4. **Polling-over-arbitrary-delay (R4)** — bounded poll-or-timeout where a condition is nameable; shared sleep primitive where not; per-site decision recorded at plan time.
5. **Module cohesion split (R5)** — page-probe health / process launch / update-check as three modules; no cross-calls, pure move.
6. **(Rejected for this package) Flattened-session multiplexing** — one socket + `sessionId`-routed commands; canonical upstream pattern but a larger rewrite than the breaches require; carried as the event-driven follow-up's candidate design.

## Risks and Anti-patterns

- **Anti-pattern: private-socket-per-call-site.** The current bypass sites (documented wedge, 2026-08-14) are the textbook instance; R1 exists to remove them. Any new consumer opening a raw socket post-refactor reintroduces the contention vector — the plan should make the factory the only importable path.
- **Risk: registry churn under TradingView updates.** `KNOWN_PATHS` is verified at call time (`verifyAndReturn`); centralizing raises the blast radius of a path change from ~15 edit sites to one — the risk inverts from scatter to single-point, which is the intent, but the plan should keep the verification-on-read behavior.
- **Risk: flatten-session temptation.** Web sources document it as cleaner; adopting it mid-package would balloon scope (RE-2). Recorded as rejected-path to keep the follow-up decision explicit.
- **Risk: sleep-policy inconsistency.** R4's per-site poll-vs-delay choice, if made ad hoc, reproduces today's scatter at a higher level of abstraction; the plan should state the decision rule once (poll when a condition is nameable, delay otherwise).
- **Assumption interactions:** RE-1 (build order), RE-2 (push scope), RE-4 (contention bar) remain stakeholder-preference items; web evidence this pass supports the agent's positions on RE-2 and RE-4 and is neutral on RE-1.
